# طراحی فنی نسخه 2.0.5 کانکتور Stalwart SCIM

## ۱. هدف نسخه

نسخه 2.0.5 با هدف ساده‌سازی نصب و قابل‌اعتماد کردن پردازش Bulk توسعه داده می‌شود. در این نسخه فقط یک JAR در WSO2 نصب می‌شود و تنظیمات عملیاتی از UI اتصال انجام می‌گیرد.

این نسخه نباید به موارد زیر وابسته باشد:
- Event Handler جداگانه WSO2؛
- ثبت subscription در deployment.toml؛
- JVM Property اختصاصی برای HYBRID؛
- متغیر محیطی اختصاصی برای Outbox؛
- JNDI یا Scope قابل تنظیم در UI؛
- JAR دوم یا Bundle جداگانه برای Observer.

## ۲. اجزای داخل یک Bundle

یک OSGi Bundle با نام org.stalwart.identity.provisioning.connector.scim شامل این اجزاست:

1. Factory مربوط به Outbound Provisioning؛
2. پیاده‌سازی عملیات SCIM 2.0؛
3. Wso2UserClaimSnapshot برای خواندن Claimهای جاری از UserStore؛
4. اتصال Declarative Services به RealmService استاندارد WSO2؛
5. HybridProfileOutbox برای صف تغییرات نام در حالت HYBRID؛
6. ScimOperationOutbox برای صف همه Mutationها در حالت BULK؛
7. Worker زمان‌بندی‌شده برای بازیابی و ارسال صف‌ها.

RealmService از طریق OSGi DS Reference تزریق می‌شود. این سرویس بخشی از WSO2 است و به تنظیم جداگانه مدیر سیستم نیاز ندارد. اگر RealmService در دسترس نباشد، تغییر نام FIRSTNAME/LASTNAME باید با خطای روشن متوقف شود؛ مقدار ناقص یا قدیمی نباید به Stalwart ارسال شود.

## ۳. قرارداد حالت‌های اجرا

| ویژگی | INDIVIDUAL | BULK | HYBRID |
|---|---|---|---|
| ساخت کاربر | POST فوری | ثبت در Outbox و Bulk | POST فوری |
| FIRSTNAME/LASTNAME/DISPLAYNAME | PATCH فوری | ثبت در Outbox و Bulk | Outbox و Bulk هر ۵ دقیقه |
| active | PATCH فوری | Outbox و Bulk | PATCH فوری |
| عضویت گروه توزیع | PATCH فوری | Outbox و Bulk | PATCH فوری |
| حذف کاربر | DELETE فوری | Outbox و Bulk | DELETE فوری |
| منبع صف | ندارد | STALWART_SCIM_OPERATION_OUTBOX | STALWART_SCIM_PROFILE_OUTBOX |
| زمان Worker | ندارد | هر ۱۵ ثانیه | هر ۵ دقیقه |

GETهای موردنیاز برای پیدا کردن User یا Group همچنان به‌صورت مستقیم و با endpoint استاندارد SCIM انجام می‌شوند؛ فقط عملیات تغییردهنده در BULK وارد Outbox می‌شوند.

## ۴. Outbox عمومی Bulk

### جدول و DataSource

- جدول: STALWART_SCIM_OPERATION_OUTBOX
- DataSource پیش‌فرض: jdbc/WSO2CarbonDB
- ایجاد جدول و Index: خودکار هنگام init اتصال
- وابستگی به تنظیم محیطی: ندارد
- محدوده صف: ترکیبی از endpoint، profile endpoint، user-store domain و fingerprint محرمانه توکن

مقدار Scope به‌صورت SHA-256 ساخته می‌شود؛ Token خام در Scope یا جدول ذخیره نمی‌شود. Endpoint و اطلاعات احراز هویت برای هر عملیات از پیکربندی زنده Connector استفاده می‌شود و Token در Outbox ثبت نمی‌شود.

### ستون‌های اصلی

| ستون | کاربرد |
|---|---|
| OP_ID | شناسه یکتای عملیات |
| SCOPE_KEY | جداسازی مقصد و محدوده اتصال |
| ENDPOINT_URL | endpoint مقصد برای همان Mutation |
| METHOD | POST، PATCH یا DELETE |
| RESOURCE_PATH | مسیر منبع SCIM |
| DATA_JSON | بدنه درخواست SCIM |
| STATUS | PENDING، IN_FLIGHT، SENT یا DEAD |
| ATTEMPTS | تعداد تلاش‌ها |
| NEXT_ATTEMPT_AT | زمان مجاز تلاش بعدی |
| LEASE_OWNER / LEASE_UNTIL | جلوگیری از پردازش هم‌زمان |
| RESPONSE_JSON | پاسخ فشرده و ضروری برای caller، در صورت نیاز |
| LAST_ERROR | آخرین علت خطا |
| CREATED_AT / UPDATED_AT | زمان ایجاد و آخرین تغییر |

### چرخه ارسال

1. Mutation نهایی SCIM ساخته می‌شود.
2. رکورد در یک تراکنش JDBC درج و Commit می‌شود.
3. تنها پس از Commit اجازه ارسال شبکه داده می‌شود.
4. تلاش فوری برای تخلیه صف انجام می‌شود.
5. Worker پس‌زمینه هر ۱۵ ثانیه نیز صف را دریافت می‌کند.
6. حداکثر ۲۵ رکورد با Lease دریافت می‌شود.
7. رکوردها بر اساس endpoint دسته‌بندی می‌شوند.
8. هر دسته در یک BulkRequest ارسال می‌شود.
9. پاسخ Bulk به ترتیب عملیات به رکوردها نگاشت و تک‌تک بررسی می‌شود.
10. موفق‌ها SENT و خطاها با وضعیت مستقل retry یا DEAD می‌شوند.

### نتیجه مبهم شبکه

قطع شبکه به معنی ناموفق بودن قطعی عملیات نیست. ممکن است Stalwart عملیات را Commit کرده باشد اما پاسخ به WSO2 نرسیده باشد.

- POST User: پیش از retry، تطبیق با externalId پایدار انجام می‌شود. تطبیق userName به‌تنهایی مجوز پذیرش حساب نیست.
- PATCH: فقط عملیات مجاز و idempotent از این مسیر استفاده می‌کنند؛ در retry نتیجه تکرار باید به همان وضعیت نهایی منتهی شود.
- DELETE: حذف مجدد منبع ناموجود به‌عنوان موفقیت idempotent قابل پذیرش است.
- پاسخ 409 برای POST فقط وقتی reconcile می‌شود که externalId منبع موجود دقیقاً با externalId مورد انتظار یکسان باشد.
- تعارض externalId به DEAD می‌رود و حساب متعلق به شناسه دیگر تصاحب نمی‌شود.

### Retry و نگهداری

- تلاش مجدد با backoff افزایشی از ۳۰ ثانیه آغاز می‌شود و حداکثر تأخیر به یک ساعت محدود است.
- پس از ۲۰ تلاش ناموفق، رکورد DEAD می‌شود.
- SENT تا ۳۰ روز نگهداری و سپس پاک می‌شود.
- DEAD برای بررسی اپراتور باقی می‌ماند.
- رکورد IN_FLIGHT پس از انقضای Lease قابل دریافت مجدد است.
- اگر بدنه Bulk از سقف تنظیم‌شده بیشتر باشد، batch به بخش‌های کوچک‌تر تقسیم می‌شود؛ یک عملیات منفرد که از سقف بیشتر باشد به DEAD می‌رود.

## ۵. معنای موفقیت برای WSO2 در BULK

کانکتور ابتدا رکورد را در Outbox ثبت می‌کند و سپس تلاش می‌کند آن را تا پایان مهلت درخواست به Stalwart تحویل دهد.

- اگر Stalwart موفقیت را تأیید کند، نتیجه موفق به caller برگردانده می‌شود.
- اگر پاسخ خطای دائمی باشد، خطا به caller برمی‌گردد و رکورد به DEAD می‌رود.
- اگر Stalwart در دسترس نباشد یا نتیجه در مهلت مشخص نشود، خطا به caller برمی‌گردد؛ اما رکورد پایدار در صف باقی می‌ماند و Worker آن را مجدداً پردازش می‌کند.
- بنابراین پاسخ خطای Provisioning لزوماً به معنی حذف شدن عملیات نیست؛ اپراتور باید Outbox را بررسی کند.

این رفتار برای جلوگیری از از دست رفتن درخواست در زمان خاموشی WSO2 طراحی شده است. WSO2 ممکن است provisioning event را نیز مجدداً ارسال کند؛ POST تکراری با externalId reconcile می‌شود و PATCHهای replace به وضعیت نهایی یکسان می‌رسند.

## ۶. بازیابی پس از restart

Outbox از حافظه فرایند استفاده نمی‌کند. داده اصلی در WSO2CarbonDB ذخیره می‌شود.

در راه‌اندازی مجدد:
1. WSO2 دیتابیس Carbon را باز می‌کند.
2. اتصال Provisioning فعال و Connector مقداردهی می‌شود.
3. Connector به‌طور خودکار DataSource استاندارد را lookup می‌کند.
4. جدول موجود را حفظ می‌کند و رکوردهای PENDING و IN_FLIGHT منقضی‌شده را شناسایی می‌کند.
5. Worker پس از شروع، صف را پردازش می‌کند.

در VM، فایل دیتابیس باید روی دیسک پایدار باشد. در Docker، مسیر دیتابیس باید روی Volume پایدار mount شود. حذف Volume یا دیتابیس، داده صف را نیز حذف می‌کند. در کلاستر، DataSource مشترک لازم است؛ دیتابیس محلی هر Node جایگزین DB مشترک نیست.

## ۷. منطق Claimهای نام بدون Event Handler

### علت تغییر معماری

Event Handler قبلی برای تشخیص Claim تغییرکرده و خواندن snapshot کامل لازم بود، اما نصب آن به JAR دوم، subscription و JVM Property وابسته بود.

در نسخه 2.0.5 خود Connector این کار را انجام می‌دهد:
- WSO2 رویداد outbound provisioning را به Connector تحویل می‌دهد.
- Connector تشخیص می‌دهد FIRSTNAME، LASTNAME یا DISPLAYNAME در attribute map وجود دارد.
- در تغییر FIRSTNAME یا LASTNAME، RealmService جاری را از WSO2 می‌گیرد.
- tenant جاری را از Carbon thread context تشخیص می‌دهد.
- UserRealm و UserStoreManager همان tenant را می‌گیرد.
- هر دو Claim نام را از UserStore می‌خواند.
- مقدار کامل displayName را می‌سازد.
- سپس مطابق حالت انتخابی، PATCH فوری یا enqueue در HYBRID انجام می‌شود.

### قواعد ایمنی

- تغییر FIRSTNAME به‌تنهایی یا LASTNAME به‌تنهایی trigger کافی است.
- برای ترکیب نام، هر دو Claim جاری باید از UserStore قابل دریافت باشند.
- اگر snapshot ناقص باشد، کانکتور مقدار قدیمی یا حدسی ارسال نمی‌کند.
- DISPLAYNAME تغییرکرده به‌عنوان مقدار نهایی displayName استفاده می‌شود.
- userName و externalId هیچ‌گاه در Update تغییر نمی‌کنند.

این روش باید در WSO2 IS 7.3.0 با UserStore اصلی و UserStoreهای ثانویه آزمایش شود. CSV Import نیز باید در محیط واقعی بررسی شود تا مشخص شود مسیر Import همان Outbound Provisioning را فراخوانی می‌کند یا خیر.

## ۸. رفتار ایمیل و شناسه

| رویداد | اقدام |
|---|---|
| تغییر ایمیل اصلی | نادیده گرفته می‌شود |
| تغییر Alias | نادیده گرفته می‌شود |
| افزودن Alias | نادیده گرفته می‌شود |
| حذف Alias | نادیده گرفته می‌شود |
| تغییر username داخلی WSO2 | نادیده گرفته می‌شود |
| ایجاد User | userName اولیه از Claim ایمیل |
| ایجاد User | externalId اولیه از Claim شناسه پایدار |
| هر Update بعدی | userName و externalId تغییر نمی‌کنند |

برای این رویدادهای صرفاً ایمیلی/هویتی، کانکتور باید پیش از lookup منبع SCIM خاتمه دهد و هیچ رکورد Outbox تولید نکند.

## ۹. نصب و تنظیمات

1. فقط JAR کانکتور 2.0.5 را در repository/components/dropins قرار دهید.
2. اگر از 2.0.4 ارتقا می‌دهید، JAR جداگانه Event Handler قبلی را حذف کنید.
3. subscription قدیمی Event Handler را از deployment.toml پاک کنید.
4. JVM Propertyهای قبلی stalwart.scim.hybrid.* را حذف کنید.
5. WSO2 را restart کنید.
6. اتصال stalwart-scim را از UI تنظیم کنید.
7. حالت INDIVIDUAL، BULK یا HYBRID را انتخاب کنید.

هیچ JAR دوم، Event Handler جداگانه، JVM Property یا تنظیم محیطی مخصوص صف موردنیاز نیست.

## ۱۰. محدودیت‌ها و آزمون‌های عملیاتی

موارد زیر فقط با Build یا تست Mock اثبات نمی‌شوند:
- تزریق واقعی RealmService در OSGi روی WSO2 IS 7.3.0؛
- دریافت snapshot Claim از UserStore اصلی و ثانویه؛
- صحت Tenant Context در Organizationهای WSO2؛
- پایدار بودن WSO2CarbonDB پس از خاموشی و راه‌اندازی مجدد واقعی؛
- رفتار Outbox در چند Node؛
- تحویل واقعی POST_SET_USER_CLAIMS یا CSV Import؛
- رفتار واقعی Stalwart Bulk در پاسخ‌های جزئی و نتیجه مبهم شبکه.

نسخه تا تکمیل این آزمون‌ها توسعه‌ای است و نباید به‌عنوان انتشار Production تأییدشده معرفی شود.
